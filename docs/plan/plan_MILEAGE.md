# План MILEAGE

## Файлы

- `backend/config/rules.php` — добавить отдельный бизнес-порог решения `400000` км, не заменяя существующий валидационный предел `max_mileage_km = 500000`.
- `backend/src/AppFactory.php` — передать новый порог из конфигурации в сервис оценки.
- `backend/src/Domain/AssessmentService.php` — после расчёта решения по LTV и до формирования ответа учесть нормализованный `$input['mileage']`.
- `tests/Unit/AssessmentServiceTest.php` — разрешить задавать пробег в тестовом payload и покрыть влияние границы на решение и `approved_limit`.
- `tests/Unit/ApplicationValidatorTest.php` — зафиксировать текущее поведение пустого пробега и независимость валидационного предела `max_mileage_km` от нового бизнес-порога.

## Шаги

1. Получить ответы заказчика по пустому пробегу и сочетанию правила пробега с уже полученным `reject`; до этого не выбирать поведение самостоятельно.
2. Добавить в секцию `vehicle` отдельный порог решения `400000` км, сохранив `max_mileage_km = 500000` как верхнюю границу валидного входа.
3. Передать новый порог в `AssessmentService` при сборке приложения в `AppFactory` и в setup unit-теста.
4. В `AssessmentService::assess()` после `DecisionEngine::decide()` и до массива ответа сравнить нормализованный пробег с новым порогом.
5. Применить согласованное правило объединения решения по пробегу с решением по LTV; итоговое решение должно согласованно определять и `approved_limit`.
6. Добавить граничные unit-тесты сервиса и отдельные проверки действующей валидации, затем выполнить `make test` и `make lint`.

## Тесты

- `mileage = 399999`: валидный пробег ниже порога; решение остаётся результатом расчёта по LTV.
- `mileage = 400000`: валидное граничное значение; решение остаётся результатом расчёта по LTV.
- `mileage = 400001`: валидное значение выше бизнес-порога; итоговое решение — `review`, если исходное решение по LTV не конфликтует с открытым вопросом про `reject`.
- Пустой `mileage`: зафиксировать тестом поведение после ответа заказчика; сейчас валидатор преобразует отсутствие поля в `-1` и возвращает ошибку валидации.
- `mileage = 500000`: остаётся валидным входом и обрабатывается новым правилом решения.
- `mileage = 500001`: по-прежнему отклоняется валидатором из-за `max_mileage_km`, а не превращается в `review`.
- Для результата `review` проверить нулевой `approved_limit`; существующие сценарии `approve`, `review` и `reject` по LTV должны остаться зелёными.

## Риски

- Нельзя заменить `max_mileage_km = 500000` на `400000`: это превратит бизнес-решение `review` в ошибку валидации.
- Без согласованного приоритета новое правило может ошибочно смягчить LTV-решение `reject` до `review`.
- Пустое поле сейчас не доходит до расчёта решения; изменение этого поведения затронет контракт валидации.
- После смены решения с `approve` на `review` важно не оставить положительный `approved_limit`.
- Новый параметр конструктора сервиса нужно одинаково передать в `AppFactory` и тестах, иначе приложение или unit-тесты перестанут собираться.
- Не входят: изменение формулы LTV, её порогов, VIN/возраста/суммы/срока, схема БД, репозиторий и интерфейс формы.

### Вопросы заказчику

2. Что делать при пустом или неизвестном пробеге: ошибка валидации, `review` или иной результат?
